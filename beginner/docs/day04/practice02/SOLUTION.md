## 先把长条件命名

`hasFailure` 和 `canFastTrack` 是对业务问题的直接回答。先得到这两个布尔值，后面的分支就能读成：

```text
如果有失败……
否则如果可以走快速通道……
否则如果已有审批……
否则……
```

这种命名并不是多写无用变量，而是避免在多个位置重复一串容易抄错的条件。

## 为什么顺序会改变答案

输入可能同时满足多条规则。例如热修复已审批，但也有一项检查失败。如果先判断热修复，代码会错误地允许快速发布。阻断条件必须先判断，`else if` 才能保证后面的规则只在“没有失败”时继续考虑。

## TODO 应怎样推进

1. 先替换两个布尔占位值。
2. 再为四个互斥分支填写对应的 `decision`。
3. 最后独立计算 `canDeploy`。它表示权限，不负责解释是哪一种就绪状态。

## 常见错误示例

```ts
if (canFastTrack) {
  decision = "Fast track";
} else if (hasFailure) {
  decision = "Blocked";
}
```

两者同时为真时会先命中快速通道，忽略失败检查。问题不在条件本身，而在优先级顺序。

```ts
const canDeploy = decision === "Fast track";
```

这会错误排除普通的 `"Ready"` 状态。权限应直接读取真正决定权限的业务条件。
